## Prioritized assessment and evidence

**1. Retain the two guards [I].** Current locations are `internal/repository/key.go:101` (`openKey`) and `internal/repository/repository.go:201` (`(*Repository).LoadUnpacked`). Historical parent crypto source and current `crypto/buffer.go:17`, `crypto/crypto.go:20–25,209–216,286–310` establish that `CiphertextLength(0)` includes both nonce and authentication tag. Before: these callers sliced the nonce before `Open` could reject undersized data. After: buffers shorter than the full overhead return an error first. For nonce-sized but tag-short inputs, this also standardizes earlier error reporting; not every newly rejected length previously panicked. Neither guard authenticates data; `Open` must still verify nonce/MAC, and decoded key/config validation remains independent.

The diff adds no production filesystem operation or new caller. It prevents subsequent slicing/decryption/decoding for short data, but does not prevent preceding reads or key derivation. Keeping checks separate is appropriate: `openKey` reads plaintext key JSON then derives a password key; `LoadUnpacked` reads an encrypted file and uses the repository key. Moving the check to shared `LoadRaw` would conflate those representations and its intentional raw-data/error contract.

Reject cache-deletion reachability as a defect [R→F].** `loadunpacked.json` and `cache-callers.json` identify shared direct site `site:2dad08db8468a86e9929ce0b2a30fe12e8900ba02af1715e96b1cc4cd5c1cb3e`, `os.Remove`, `internal/backend/cache/file.go:150`. Reverse edges show `Cache.remove ← Cache.Forget ← Repository.LoadRaw`, reached from `LoadUnpacked` and independently `LoadKey ← openKey`, including hinted and enumerated key callers. These are multiple callers of one site, not duplicate deletions.
