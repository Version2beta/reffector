# Reffector — post-Ralph technical review

**Review target:** Reffector `d766ee95bde0041549cedc1bdbc9a1a6d3a0ef29`. The checkout was dirty before review; implementation and benchmark artifacts were read-only. No implementation or existing report was edited; this review writes the requested report only. Python validation may have refreshed the pre-existing untracked `tools/effect_investigation/__pycache__/`. No additional model investigation or external experiment was run.

## Executive assessment

The deterministic packet builder has several strong boundaries: it validates report IDs and graph references, preserves candidate/established relationship labels in its graph projections, authenticates retrieved file contents by whole-file SHA-256, checks repository containment, and represents graph/source truncation and deferral. The optional model adapter also pins a provider/model in its CLI arguments and checks the response metadata.

The model-assisted layer does **not** yet provide the stronger evidence verification and aggregation guarantees implied by milestones 6–7. Its output citations are only checked against any recursively discovered `id` in the packet; the separate static verifier is narrow and is not called by the invocation/persistence path. The aggregator trusts opaque IDs and groups same-site findings without requiring a shared obligation or resource. Persisted artifacts can also contradict the latest run after a failed rerun in a reused directory. These are concrete boundary defects, not evidence that the recorded model outputs were false.

The M8 comparison is a traceable one-pair null result, but it does not test Reffector's evidence selection: both arms received the same excerpts, including the same omission, and treatment added mostly effect-site framing rather than caller/return evidence. Recommendation: **fix specific blockers first** before treating the model workflow or aggregation as evaluation-ready.

## 1. Implementation assessment

### What is working

- `tools/effect_investigation/investigate.py:86-157` validates stable EffectReport site/node/edge ID shapes, graph endpoints, candidate flags, relationship resolutions, and reverse-graph references. The argument-provenance and control-flow validators also join on canonical site IDs and check API identity (`158-219`, `241-368`).
- Graph construction and compaction retain edge IDs, edge kinds, `candidate` flags, and resolutions (`587-750`, `903-928`). The packet reducer reports graph connectivity separately from explicit reference completeness and records deferred references and truncation (`948-984`, `986-1150`, `1182-1254`). This is a useful distinction: a compact path description is not silently relabeled as a complete relationship catalog.
- `investigate.safe_source` resolves source under a supplied root, checks the manifest digest, and rejects paths that resolve outside it (`506-535`). `retrieve_source_excerpt` in `model_investigation.py:22-62` checks required reference fields, one-based inclusive ranges, the whole-file digest, symlink components, root containment, and the excerpt byte limit. `prepare_model_packet` drops cached excerpt text and reads only the supplied references (`68-81`). The integrity of a *selected* excerpt is stronger than its completeness.
- The Pi adapter starts a subprocess per call with `--no-session`, disables tools/MCP/extensions/skills/context files, specifies provider/model, applies request/response/event-size checks, rejects nonzero exit, malformed JSON and metadata mismatch (`97-154`). With the default runner, a 120-second timeout raises from `subprocess.run`, is converted to a generic `InvestigationError`, and `run_and_persist` records an error rather than a result; partial timeout output and the underlying exception type are not persisted. This fails closed but weakens diagnosis/reproduction. Actual M5 and M8 raw events include complete session/turn endings and assistant metadata matching `openai-codex` / `gpt-6-luna`; the calls were separately recorded. Response metadata verifies the provider/model labels reported by Pi, not a cryptographic identity for the executable or endpoint.

### Ranked concerns and smallest corrections

#### 1. High — citation validation does not preserve evidence type or prove support

`invoke_isolated` checks each returned evidence string against `_ids(packet)` (`model_investigation.py:84-95`, `261-308`). `_ids` recursively collects every string value under a key named `id`, not just evidence IDs. A response can therefore cite `site:def`, a graph node, or a candidate edge as supporting evidence. I reproduced acceptance of `supporting_evidence: ["edge:candidate"]` where the packet edge is explicitly `candidate: true` and `resolution: "candidate_vta"`; the packet had no evidence record for that edge. The schema then accepts a free-form hypothesis asserting the relation is established. This does not show that M5 made such a claim; it shows the current boundary does not prevent one.

`verify_static_claims` is a separate helper and is not called from `invoke_isolated` or `run_and_persist` (`156-185`, `310-355`). It checks a relationship claim's resolution string against a packet evidence row and checks a source claim's path and optional API. It does not verify relationship endpoints/canonical edge identity, or that the cited source text/digest/range supports the claim. A reproducible false-support example passes: packet `operation.api = "os.RemoveAll"`, `source_excerpts = [{"path":"pkg/file.go"}]` with no text/hash/range, and a source claim for that path/API returns `True`. The current positive unit test uses exactly this kind of path-only excerpt (`test_model_investigation.py:34-49`).

The M5 output also uses the single generic `ev:operation` ID in both `supporting_evidence` and `contrary_evidence`; its statement establishes that a cleanup closure executes `os.RemoveAll`, not the later-return/caller behavior being investigated (`reports/m5-iteration30-real-investigation/request.json`, `result.json`). Citation validity is not entailment.

**Smallest correction:** use typed, unique evidence references in the response schema; validate citations only against the corresponding canonical evidence table, including exact site/API/edge resolution and source path/range/digest. Make structured claim verification part of the same invocation pipeline, and keep free-form hypotheses explicitly unverified. Do not claim that structural matching verifies semantic truth.

#### 2. High — aggregation groups on trusted labels, not verified shared facts

`aggregate_findings` validates that `site_id`, `effect_id`, `resource_id`, `obligation_id`, caller-segment IDs and evidence IDs are nonempty strings (`188-259`). It never resolves them against a packet, graph, source excerpt or evidence store. Its cross-site grouping therefore accepts invented but equal IDs as if they were source-supported. More directly, every finding enters a same-site bucket keyed only by `(effect_id, site_id)` (`224-227`), even when resource and obligation differ. I reproduced two findings with the same site/effect but different resource and obligation IDs being grouped. Records need not contain a shared hypothesis/obligation or any evidence resolving those labels.

The output does preserve `status_by_finding`, the evidence-ID union, and `provisional: true` (`247-258`), which limits but does not remove the conflation risk. Statuses are only prefilled labels; the function does not validate them semantically. The allowed status set has `contradicted`, `plausible-unverified`, `supported-static`, `runtime-confirmed`, and `unresolved`, but no distinct `unsupported` state.

**Smallest correction:** require source-resolved identities for shared caller/resource/obligation evidence, and require a defined equivalence key before grouping (including operation/API where cross-site grouping is intended). Do not let same-site/effect alone merge unrelated hypotheses. Retain per-finding uncertainty and add an explicit unsupported status if that is a required distinction.

#### 3. Medium — failed reruns leave contradictory artifacts

`run_and_persist` writes whichever artifacts apply but does not clear artifacts from earlier runs in the same directory (`310-355`). I ran a successful call followed by a malformed-output failure in one temporary directory: the second manifest said `outcome: "error"`, `error.json` existed, and the prior successful `result.json` also remained. A consumer that reads the result without checking the manifest can mistake stale output for the failed run. A later success can likewise leave an old `error.json`. Sequential writes are also not atomic if persistence itself fails partway through.

**Smallest correction:** make the artifact directory unique per invocation, or atomically replace a complete run directory and remove stale success/error/event files before publishing the new manifest.

#### 4. Medium — source ranges are authentic but not guaranteed complete

The source retrieval helper returns precisely the requested range; it does not expand to a function or caller boundary (`22-62`, `68-81`). Empty `source_refs` is accepted by `prepare_model_packet` and yields an empty excerpt list without an explicit completeness state. `investigate.build` does better when given a program model: it selects operation-local and owner/frontier/boundary declarations (`1351-1408`) and tracks unavailable/deferred source. But that completeness information is not required by the model preparation boundary, and no general rule ensures the evidence needed to interpret an operation was selected.

This failure is observed in the benchmark: M8 references `loading.go:73-93`; the relevant `return cfg, cleanup, nil` is `loading.go:94`. The hash authenticates the file, not the omission. A known range end is visible, but no packet completeness claim says the rest of the function/caller was examined.

Source reference IDs are also trusted as input: `retrieve_source_excerpt` returns `reference["id"]` unchanged and does not recompute a canonical ID from path/digest/range. Duplicate or misleading IDs are not rejected. The core builder produces stable source IDs, but the retrieval boundary does not require those IDs. Also, retrieval reads the entire file before enforcing the 16 KB excerpt limit (`45-61`); this does not bound memory/read cost for a huge repository file. No such oversized-file failure was observed here.

**Smallest correction:** require a packet schema with explicit source-selection completeness/unavailable/deferred fields and validate each reference ID against its canonical path/hash/range tuple. For operation questions about callbacks, errors or cleanup, include the complete owning declaration and relevant caller declaration or mark the evidence incomplete. Cap source-file bytes or hash/read in bounded chunks.

#### 5. Medium — event limits are enforced after capture and persistence handoff

The adapter calls `event_sink(completed.stdout)` before checking the 256 KB limit (`model_investigation.py:125-131`). `subprocess.run(capture_output=True)` has already buffered the entire output, and `run_and_persist` appends it before the adapter rejects the size. The call fails closed as a result, but an over-limit stream can still be retained in `provider-events.jsonl` and there is no memory/output cap during capture. The unit test only asserts the error, not that the sink/artifacts remain bounded (`test_model_investigation.py:160-170`).

The adapter also accepts a successful `message_end` without requiring any session/turn completion event; the fake successful stream in the unit test contains only `message_end` (`138-160`). Actual M5/M8 streams do end with `agent_end`/`agent_settled`. A zero exit plus complete assistant message may be sufficient under the Pi CLI contract, but the implementation does not verify overall-session completion if that is required.

**Smallest correction:** bound output while reading (not after full capture), reject before event persistence, and test that an oversized stream leaves no oversized artifact. If Pi's contract requires a terminal event, require and test it; otherwise document that zero exit plus a completed assistant message is the chosen completion contract.

### Evidence integrity, uncertainty and retrieval summary

Candidate/established edge labels are preserved by the deterministic packet builder; there is no evidence that the core graph reducer itself promotes candidate edges. The risk is at the model wrapper/verifier boundary, where arbitrary packet IDs become evidence citations and hypotheses are not semantically checked. The source retrieval path containment/digest checks are substantively sound for a selected reference, while selection coverage and ID-to-reference binding remain weak. The symlink unit test permits rejection either for an outside-root target or a symlink (`test_model_investigation.py:125-135`), so it does not specifically exercise the symlink-component branch; a symlink to an in-root file would make that assertion discriminating.

`verify_static_claims` establishes only structural equality for the fields it checks. It cannot establish a hypothesis's truth, and the workflow does not assign verified claim states. Aggregation preserves the statuses it is given, but it cannot establish that those statuses, resource IDs, obligations, or caller segments are true.

### What these tests establish—and do not

The Python suite meaningfully exercises packet schema/ID joins, graph reduction accounting, source hashes/ranges/containment, candidate-edge retention, provider/model mismatch, nonzero exit, response limits, and several failure paths. The integration test compiles Reffector and checks that a candidate function-value edge and structural CFG facts stay unpromoted. These are useful boundary tests.

The suite can still pass while important incorrect implementations remain:

- `test_independent_static_claim_checks_reject_promotion_and_fabrication` tests nonexistent path, API mismatch, and resolution mismatch, but its positive source claim has no text/hash/range. It does not reject a semantically false claim tied to an existing path/API; the reproducer above passes today.
- `test_aggregation_rejects_category_or_similar_resource_false_groups` tests distinct opaque keys. It does not test same-site different obligations/resources, or whether shared caller/resource/obligation IDs resolve to evidence. The positive case labels arbitrary strings “source supported.”
- `test_malformed_wrong_id_and_unbound_citation_fail_closed` rejects an ID absent from the packet, but does not reject a citation to a wrong-kind ID present in the packet.
- The `message_end`-only provider fixture positively accepts a stream with no explicit overall-session terminator. The event-size test does not check event-sink or persisted-artifact bounds, and no test exercises `subprocess.TimeoutExpired` and timeout diagnostics.
- The symlink test can pass by rejecting an outside-root resolution before the explicit symlink check. Use an in-root symlink to test that branch.
- The new `assertNotIn("established", resolution)` checks in `test_investigate.py` are redundant after exact equality with `candidate_vta` / `candidate_function_value` (`475-483`). They do not prove any additional non-promotion property.
- There is no end-to-end test proving `run_and_persist` invokes `verify_static_claims` or feeds verified claims to aggregation; current call sites do neither.

These gaps are not failures of the commands just run. They limit what a green result proves.

## 4. Benchmark interpretation

1. **Useful information unavailable to control?** Treatment added an operation/site ID, `fs.delete` effect label, a generic statement that `os.RemoveAll` is used by a cleanup closure, and caveats. Those are traceable but largely restate the question/source. It did not add the critical return relationship or additional caller evidence.
2. **Comparable context budgets/evidence?** Both received the same 26 source lines: `loading.go:73-93` and `analyzer.go:139-143`. Treatment request size was 4,888 bytes versus 1,583 for control; provider-reported input was 1,688 versus 629 tokens. Treatment also repeats its source excerpts inside `reffector_packet` and again in `source`. Thus source lines were matched, but total context was not; treatment used about 2.7× the input tokens. Reported elapsed time was 9.365 s for treatment and 11.15 s for control; reported output usage was 464 versus 489 tokens. Those are single-call observations, not performance evidence. Provider-reported costs were $0.0004008 and $0.0003074 respectively, not independently billed amounts.
3. **Did Reffector select relevant evidence?** Not in this pair. The treatment packet carries no caller graph, edge-resolution evidence, provenance, control-flow summary, or source-selection coverage. It adds information but does not demonstrate effect-directed retrieval of the fact needed by the question.
4. **Why did both miss `loading.go:94`?** Every input excerpt ends at line 93. The source-only and supported arms were therefore both unable to cite the return of `cleanup`; each correctly described that point as unestablished from the supplied excerpt. The shared omission explains the shared one-point loss.
5. **Could Reffector have selected the omitted relationship?** Deterministically, potentially: `investigate.build` can select operation-owner/frontier/boundary declarations and graph-linked callers (`1351-1408`), and its source references carry line ranges and whole-file digests. If the EffectReport includes the relevant closure/caller relations and the program model supplies their complete declarations, line 94 and the caller defer can be selected without a model call. However retrieval only returns requested ranges; it does not infer that a manually supplied range ending at 93 is incomplete. This pair did not use that pipeline output, and no saved graph evidence establishes that the necessary return/caller relation would be recovered in this specific case.
6. **Was the task discriminating?** No. It was a small one-site cleanup question, both arms had the same hand-selected omission, and the treatment did not carry the call graph. It could test cautious reasoning over fixed excerpts, but not the proposed advantage of effect-directed context selection.
7. **What does 9/10 vs 9/10 establish?** Only that these two calls scored equally under this five-item rubric on this single task. It establishes no observed score gain here. It neither demonstrates usefulness nor uselessness; the common missing source line and treatment construction prevent a causal efficacy conclusion. The fixed control-first order, even with fresh sessions, is another limit. The extra treatment context and token use are observed costs, not proof of no future benefit.

## Recommendation: **fix specific blockers first**

The deterministic analyzer/packet core is suitable for continued bounded evaluation, but the current model workflow is not ready to claim source-backed verification or safe related-finding aggregation. Before the next model comparison, bind citations to typed canonical evidence, make verification part of the persisted invocation, prevent stale run artifacts, and make cross-finding group criteria evidence-resolved. Then preflight the rclone packet and freeze the experiment before calls.

## Three highest-value next actions

1. Integrate typed, source-bound claim verification into the invocation path and add regressions for wrong-kind citations and unsupported source claims.
2. Require evidence-backed operation/resource/obligation equivalence in aggregation; test distinct same-site findings and unrelated cross-site operations.
3. Build and inspect the rclone pre-fix Reffector packet at the pinned revision, then independently validate the regression test pre/post before preregistering model calls.
